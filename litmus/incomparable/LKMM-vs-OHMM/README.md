# LKMM <-> OHMM  (incomparable)

The Linux Kernel Memory Model (LKMM) and the Operational Happens-Before Model (OHMM) are both *syntactic-dependency-preserving* models: each tackles the out-of-thin-air problem by tracking the syntactic dependencies between memory events and forbidding the reordering of dependent events, so both FORBID the canonical thin-air load-buffering outcome (`r1=r2=42` fabricated from nothing). But they are built over completely different primitives and machines. LKMM is an axiomatic `cat` model over the Linux kernel's own primitives — `READ_ONCE`/`WRITE_ONCE`, `smp_mb`/`smp_wmb`/`smp_rmb` barriers, release/acquire, and RCU (`rcu_read_lock`/`synchronize_rcu`) — whose ordering is assembled from explicit barriers chosen to be sound on x86/Armv7/Armv8/POWER. OHMM is an operational, JMM-repair model: a Java-style abstract machine with a global event buffer (in which independent, non-dependent events may be reordered before they propagate into a global history-based memory) plus a replay mechanism used to simulate speculative execution. Because OHMM admits reorderings of independent accesses that LKMM's barrier-based ordering forbids, while LKMM expresses barrier and RCU orderings OHMM has no primitive for, neither model's behaviours are a subset of the other's — they are incomparable.

## Direction 1 -- OHMM allows, LKMM forbids: reordering of independent accesses

`MP-reorder.litmus` is message passing with two *independent* writes (to `x` then `y`) on P0 and two independent reads (`y` then `x`) on P1, with no syntactic dependency linking the pairs. OHMM's abstract machine holds events in a global event buffer where independent events may be reordered before propagating, so the store to `y` can become visible before the store to `x`, yielding `1:r1=1 /\ 1:r2=0`. The survey states explicitly that OHMM "is weaker than JMM for lockless programs ... such as the reordering of independent memory accesses that is not valid in JMM," and more generally Table 3 of the survey gives LKMM and OHMM *different* sound-transformation profiles (LKMM: `- + + - + + + - -`; OHMM: `+ - - + - - - + -`), confirming that each validates transformations the other does not. With the corresponding Linux write/read barriers in place, LKMM forbids this outcome; and there is no OHMM `cat` model, so the OHMM verdict is cited, not executed.

## Direction 2 -- LKMM allows, OHMM forbids/cannot express: kernel primitives

LKMM directly models primitives that OHMM's Java-style machine has no counterpart for: full/write/read memory barriers (`smp_mb`, `smp_wmb`, `smp_rmb`) and especially RCU, where a grace period (`synchronize_rcu`) is guaranteed to order pre-existing read-side critical sections against later updates. These orderings are part of LKMM's permitted/forbidden verdicts and cannot even be written down in OHMM, so behaviours LKMM constrains via these primitives lie entirely outside OHMM's expressible language. (See the sibling `../C11-vs-LKMM` pair for the RCU witness `RCU.litmus`.) Because each model states an ordering the other cannot, neither is a subset of the other.

## Running

Neither side is machine-run for the separating test. OHMM has no herd7/`cat` formalisation (it is an operational model defined by an abstract machine in the paper), and the independent-access reordering of `MP-reorder.litmus` is an OHMM-specific behaviour, not an LKMM execution. LKMM itself *does* run in herd7 against `linux-kernel.cat` (and the Direction-2 RCU witness can be executed there as in `../C11-vs-LKMM`), but for the cross-model separating outcome the verdicts are CITED from the literature, not produced by a single checker.
